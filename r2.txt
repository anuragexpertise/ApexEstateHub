## Phase 2 — GST engine

This is the biggest gap and the one with the most billing-engine surface area, since GST has to be evaluated **per-apartment, per-month**, not just once per society.

**2a. Threshold-check logic**
GST only applies when *both* conditions hold: society turnover > ₹20L *and* that specific member's monthly maintenance > ₹7,500. That second condition means the check can't be done once at the society level — `fn_auto_generate_receivables` needs to evaluate it per apartment, per billing cycle, since two flats in the same society can have different maintenance rates (the schema already supports per-apartment overrides via `apt_charges_fines_basis.apt_maintenance_amount`) and therefore different GST liability.

**2b. Exempt-component separation**
Statutory pass-through collections (property tax, water charges billed at actual recovery) must stay GST-exempt even when the rest of the bill crosses the threshold. This means a single "maintenance" line can no longer be one lump sum for GST purposes — it needs a breakdown between GST-applicable components and pass-through exempt components. This connects directly to the fund-splitting requirement in Phase 3, since both need the same underlying capability: a bill that resolves into several distinctly-taxed/distinctly-allocated line items instead of one number.

**2c. SAC 9995 + tax account additions**
Add GST output-tax accounts (CGST payable, SGST payable) to the chart of accounts, following the same pattern the TDS account already uses (`fn_resolve_tds_account`) — a `fn_resolve_gst_accounts` equivalent. The receivable/receipt generation path needs a third leg (base amount → income account, GST amount → GST payable accounts) analogous to how `fn_verify_payment` already splits a payment into a net-expense leg and a TDS leg.

**2d. GST return support**
Not full GSTR-1/3B filing automation (out of scope for a v1), but the system should be able to produce the underlying data — taxable value, exempt value, tax collected by rate — as a report, since that's what actually gets typed into the GST portal each period.
## Phase 2 — Bill splitting: detailed design

I traced this all the way through `fn_pay_apartment_dues_fifo` and `fn_apply_receivable_interest` to see how a multi-line bill would actually behave once money starts moving, not just how it gets created. That surfaced a real, previously-invisible risk — covered below, since it's the part most likely to quietly corrupt the ledger if missed.

### The core decision: multiple `receivables` rows per bill period, not a JSON breakdown

Confirmed against `fn_pay_apartment_dues_fifo`, `fn_apply_receivable_interest`, and `fn_check_orphan_receivables`/`fn_check_duplicate_receivables` — all three already operate as row-level `FOR ... LOOP`s over `receivables`, not as single-row lookups. That means "one row per fund line" slots into existing machinery with far less rewriting than a single-row-with-JSON-breakdown approach, which would require every one of those functions to learn how to parse and partially settle a nested structure. Reuse over reinvention here.

**Grouping key:** add `bill_group_id UUID` (or a `bill_id` referencing a new lightweight `bills` header table — see below) to `receivables`, generated once per apartment per billing cycle, shared across every line (`SocM`, `SinkFund`, `RepFund`, GST-on-`SocM` if applicable). This is purely a display/grouping key — FIFO settlement, interest, and status tracking all continue to operate per-row exactly as they do today. The UI collection screen groups by `bill_group_id` so a resident sees one consolidated "₹6,200 due — Apr 2027" line, not four separate charges, even though four `receivables` rows exist underneath.

I'd lean toward the UUID-on-existing-table approach over a new `bills` header table for v1 — it's a smaller migration, and a header table only earns its keep once you need bill-level metadata (a single PDF invoice number, a single due-date override at the bill level rather than per-line) that doesn't fit naturally on `receivables` itself. That's a real future need, but not one this phase requires.

### Rewriting `fn_auto_generate_receivables`

Currently: one `INSERT INTO receivables` per apartment per month, one `acc_id`. Restructured:

1. Resolve the billing basis as today (`apt_charges_fines_basis`, prorated for partial months) — but where it currently produces one `v_base`, it now needs to look up **all active fund-rate lines** for that apartment/period: `apt_maintenance_rate`, plus the new `apt_sinking_fund_rate` and `apt_repair_fund_rate` from Phase 1's schema extension.
2. Generate `v_base_maint`, `v_base_sinking`, `v_base_repair` — same proration math (`overlap_days / days_in_month`) applied independently to each, since a mid-month rate change or a mid-month move-in should prorate every fund line consistently, not just maintenance.
3. **GST check happens here, per line, per apartment** — this is where Phase 1's per-apartment maintenance amount and the ₹7,500 threshold actually get evaluated (confirmed: `apt_charges_fines_basis.apt_maintenance_amount` already varies per apartment, so this can't be hoisted out to a society-level check). If `v_base_maint > 7500` AND society turnover > ₹20L, compute a GST line (`v_gst_amt = v_base_maint * 0.18`) as an **additional row**, not baked into `v_base_maint` itself — GST must be separately visible on the bill and separately postable to CGST/SGST payable accounts, not folded into taxable-value income.
4. Sinking Fund / Repair Fund lines are **not** GST-eligible under the exempt-collection carve-out (statutory pass-through), so they get no GST line regardless of amount — worth double-checking against current CBIC circulars at implementation time, since GST-on-society-collections has had contested interpretations, but the safe default is: GST only on the maintenance component that crosses the per-member threshold.
5. Insert one `receivables` row per line, all sharing the new `bill_group_id`, each with the fund's own `acc_id` (Sinking Fund / Repair Fund / GST-payable accounts from Phase 1/3's chart-of-accounts additions).

### The risk I found: `fn_pay_apartment_dues_fifo` posts one lump ledger leg, not one per account

This is the part that actually matters most. Right now, `fn_pay_apartment_dues_fifo` takes the *entire* payment amount and posts it as a **single** `Cr` transaction leg against `v_acc_id` — resolved once, from whichever receivable is oldest — then separately loops through `receivables` rows updating `paid_amount`/`paid_principal` bookkeeping. The bookkeeping loop is already correctly multi-row; **the actual general-ledger posting is not.**

Concretely: today, if a resident pays ₹6,200 covering one maintenance row and one sinking-fund row, this function would credit the *entire* ₹6,200 to whichever account belongs to the single oldest receivable — the sinking fund contribution would never reach the Sinking Fund account in the ledger at all, even though `receivables.paid_amount` correctly shows it as settled. The dues-tracking would look right; the trial balance would be wrong. And since the mutuality tax report and the fund-escrow reporting from Phase 1/3 both read off the ledger, not off `receivables`, this isn't a cosmetic gap — it would silently misstate exactly the numbers this whole compliance effort exists to get right.

**Required fix:** rewrite the settlement loop to accumulate `v_take` per distinct `acc_id` (a local hash/array of account→amount, built up across the existing FIFO loop iterations) and, after the loop completes, emit **one `Cr` transaction leg per distinct account actually settled**, each for its accumulated amount, all sharing the same `journal_id` so they remain one atomic payment event. This is a genuine rewrite of the posting section, not a schema-only or generation-only change — flagging it now so it's estimated and reviewed as its own unit of work, not discovered mid-implementation of Phase 2.

### Interest — a policy decision, not just a mechanical one

`fn_apply_receivable_interest` already loops per-row and would apply interest independently to each overdue line once split. That's mechanically fine, but raises a real bye-law question: should an overdue Sinking Fund contribution accrue the same late-interest as overdue maintenance, or are escrow/reserve fund contributions typically penalty-exempt under your users' bye-laws? I don't know the answer generically — it varies by society's own bye-law text — so I'd add a `charges_interest BOOLEAN` flag to the per-fund rate configuration (alongside the new `apt_sinking_fund_rate`/`apt_repair_fund_rate` fields) rather than hardcoding either behavior, and default it to `TRUE` (matching current maintenance behavior) unless told otherwise.

### Advance credit

`fn_pay_apartment_dues_fifo`'s excess-payment handling (the `IF v_remaining > 0` block banking overpayment as a `status='credit'` row) currently books the whole excess against `v_acc_id` — same single-account assumption as the main settlement path, same fix needed: once every open line across every fund is settled, remaining excess should probably default to the *maintenance* account specifically (not sinking/repair — a resident overpaying likely intends it as a maintenance credit, not an unsolicited extra fund contribution), which is actually simpler than the main settlement fix, just needs the fallback `v_acc_id` resolution to explicitly target the maintenance account rather than "whichever row happened to be oldest."

### `fn_verify_receivable` (manual receipt entry) — actually the safe path, and the template to copy

Unlike the FIFO bulk-pay function, `fn_verify_receivable` operates on one `receivables` row at a time, and already posts each row's amount to *that row's own* `acc_id`. Once multi-line billing exists, this function needs no fix — but there's a UX gap: if a resident's consolidated bill is three rows (maintenance/sinking/repair) under one `bill_group_id`, an admin manually verifying a paper receipt shouldn't have to enter three separate receipts for what the resident experienced as one payment.

**Add `fn_verify_receivable_by_bill_group(p_bill_group_id, p_confirmed_by, p_mode, p_amount)`** — a thin wrapper that loops over every row sharing that group and calls the existing `fn_verify_receivable` per row (FIFO-ordered within the group if the payment doesn't cover the full group total). This is low-risk specifically *because* it just orchestrates the already-correct single-row function rather than reimplementing posting logic — and it's the same "one Cr leg per row" pattern the FIFO rewrite needs, just already proven correct here. Worth building this wrapper first, actually, since it validates the grouping/proration logic on the lower-risk path before touching the bulk FIFO function.

### Found a second integrity-checker gap: `fn_check_duplicate_receivables` will false-positive on every split bill

```sql
GROUP BY r.entity_id, r.role, r.period_month
HAVING COUNT(*) > 1
```

This flags *any* apartment with more than one receivable row in the same month as a duplicate — with no awareness of `acc_id` at all. Today that's correct, because one row per apartment per month is the invariant. Once split billing ships, every single consolidated bill (3+ legitimate rows, same period, different accounts) becomes a false positive. Left unfixed, this either buries real duplicates in noise or trains whoever reviews this report to ignore it entirely — the worse of the two outcomes, since it silently defeats a check the system relies on for data-integrity confidence.

**Fix:** `GROUP BY r.entity_id, r.role, r.period_month, r.acc_id` instead — same account, same period, more than one row is still a real duplicate; different accounts, same period is now the expected shape.

## Phase 2d — GST return support

### Data source: the ledger, not `receivables`

Once Phase 2's split-billing lands, GST collected lives as `Cr` legs on the new CGST/SGST payable accounts (resolved via `fn_resolve_gst_accounts`, same pattern as `fn_resolve_tds_account` above), tagged `source_table='receivables'` / `source_id` back to the specific bill line. That's the join path — same principle as everything else this session: the ledger is the single source of truth, intermediate tables (`receivables`) are working state, not the record.

**New function: `fn_gst_summary_fy(p_society_id, p_fy)`**

Returns one row per month within the FY (GST periodicity is monthly for most societies, quarterly for QRMP-eligible ones — I'd build monthly and let the Excel layer sub-total into quarters, since monthly-to-quarterly is a free rollup but quarterly-to-monthly loses information):

```
period_month | taxable_value | cgst_collected | sgst_collected | exempt_value | total_bills_gst_applicable | total_bills_exempt
```

- `taxable_value` — sum of the maintenance-component base amount on every `receivables` row that had a GST line generated for it (join on `bill_group_id`, filter to lines where a sibling GST-line row exists in the same group).
- `exempt_value` — sum of Sinking Fund / Repair Fund lines, plus maintenance lines that stayed under the ₹7,500 per-member threshold, plus statutory pass-through items — everything that's *not* `taxable_value`, from the same billing data.
- `cgst_collected`/`sgst_collected` — straight sums of the `Cr` legs on the two GST payable accounts for that month, from `transactions`.

This mirrors `fn_fy_closing_report`'s shape closely enough that the Excel formatter can reuse most of `ledger_export.py`'s existing styling helpers (`_FONT_HEADER`, `_FILL_HEADER`, `_FMT_AMT`, the row-writing loop) rather than inventing a new visual language — worth building this as `database/gst_export.py` alongside `ledger_export.py` and `cashbook_export.py`, following the same `generate_X_excel(db, society_id, fy)` signature convention so it slots into the existing `download_fy_export` callback dispatch (`entity == "gst_summary"`) the same way `ledger_index`/`ledger`/`cashbook` already do.

### What the sheet needs to look like

Two sheets, since GSTR-1 (outward supplies, what you *filed*) and GSTR-3B (summary return, what you *paid*) ask for the numbers in slightly different shapes:

- **"Taxable Supplies"** — month-by-month taxable value, tax rate (18% split 9%/9%), CGST, SGST, matching GSTR-1's Table 4/5 outward-supply shape closely enough to transcribe by hand into the portal.
- **"Summary"** — one FY-total row: total taxable value, total tax collected, total exempt value, total turnover (taxable + exempt) — this is the number that also feeds back into Phase 1c's turnover threshold check for *next* year, so it's worth exposing as its own queryable value (`fn_gst_summary_fy`'s final row, or a small `fn_society_turnover_fy` helper), not just buried in a spreadsheet cell.

**Deliberately not building:** GSTIN-matching, e-invoice IRN generation, or a GSTN API integration. Those require registration as a GST Suvidha Provider or ASP and are a different scale of project — flagging this boundary explicitly so it's a documented decision, not a silent gap someone discovers later assuming it was in scope.

## Phase 4d — Form 16A / 26Q export

### Data source: same principle, `transactions` joined back through `expenses`

TDS deducted lives as `Dr` legs on the TDS-payable account (`fn_resolve_tds_account`, already exists), tagged `source_table='expenses'` / `source_id`. Since `expenses` has `entity_id`+`role='vendor'` but no PAN (that's Phase 1's job — `vendors.pan_number`), the report needs a three-way join: `transactions` (the actual deducted amount, dated) → `expenses` (which vendor, which TDS section — Phase 1's `accounts.tds_section` inherited onto the expense) → `vendors` (PAN, name, GSTIN).

**New function: `fn_tds_summary_fy(p_society_id, p_fy, p_quarter)`** — quarterly, not monthly, since 26Q is a quarterly return (Q1 Apr–Jun, Q2 Jul–Sep, Q3 Oct–Dec, Q4 Jan–Mar — note this straddles the April–March FY boundary in the *same* pattern the FY itself already uses, so no new date-math beyond what `fn_fy_closing_report` already does for FY boundaries).

```
vendor_name | vendor_pan | tds_section | gross_amount_paid | tds_deducted | net_paid | payment_date
```

One row per TDS-bearing payment (not aggregated per vendor) — 26Q actually wants per-transaction deduction records, not vendor totals, since deduction date matters for interest-on-late-deduction calculations if a filing is ever late. A separate **vendor-summary sheet** (one row per vendor, section, cumulative annual total) is still useful as a human-readable cross-check against Phase 4b's ₹1,00,000 annual-threshold tracking — that's actually the same query, just grouped differently, so build it as a second sheet in the same workbook rather than a second report.

**Vendors with no PAN captured** (a real possibility per Phase 1's design — TDS can be deducted before PAN is on file) should be flagged distinctly on the report, not silently blanked — a missing PAN on a 26Q line is a filing-blocking problem, and it's much better for this report to surface it loudly (a highlighted row, a warning count in the summary) than for someone to discover it at actual filing time.

**Deliberately not building:** actual TRACES/26Q e-filing (requires a Tax Deduction Account Number registration flow and a specific government-mandated file format/validation utility, again a different-scale integration) — same "structured report, not filing automation" boundary as 2d, for the same reason.

RETURNS TABLE(transaction_id INT, allocated NUMERIC, unallocated NUMERIC, journal_id INT)

        IF v_first_trx_id IS NULL THEN v_first_trx_id := v_trx_id; END IF;
    END IF;

    -- Accumulate principal (and interest when no separate interest_acc_id)
    -- per acc_id for batch posting after the loop.
    IF v_pay_prin > 0 THEN
        v_acc_idx := NULL;
        FOR i IN 1..array_upper(v_acc_ids, 1) LOOP
            IF v_acc_ids[i] = rec.acc_id THEN
                v_acc_idx := i;
                EXIT;
            END IF;
        END LOOP;

        IF v_acc_idx IS NULL THEN
            v_acc_ids := array_append(v_acc_ids, rec.acc_id);
            v_acc_totals := array_append(v_acc_totals, v_pay_prin);
        ELSE
            v_acc_totals[v_acc_idx] := v_acc_totals[v_acc_idx] + v_pay_prin;
        END IF;
    END IF;

    IF v_pay_int > 0 AND rec.interest_acc_id IS NULL THEN
        v_acc_idx := NULL;
        FOR i IN 1..array_upper(v_acc_ids, 1) LOOP
            IF v_acc_ids[i] = rec.acc_id THEN
                v_acc_idx := i;
                EXIT;
            END IF;
        END LOOP;

        IF v_acc_idx IS NULL THEN
            v_acc_ids := array_append(v_acc_ids, rec.acc_id);
            v_acc_totals := array_append(v_acc_totals, v_pay_int);
        ELSE
            v_acc_totals[v_acc_idx] := v_acc_totals[v_acc_idx] + v_pay_int;
        END IF;
    END IF;

    v_remaining := v_remaining - v_take;
END LOOP;

-- Emit ONE Cr leg per distinct acc_id actually settled, all sharing
-- the same journal_id. This is the core fix: previously the entire
-- lump payment was credited to whichever single acc_id belonged to
-- the oldest receivable, silently misattributing every other line.
IF array_upper(v_acc_ids, 1) IS NOT NULL THEN
    FOR i IN 1..array_upper(v_acc_ids, 1) LOOP
        INSERT INTO transactions(
            society_id, entry_side, trx_date, acc_id, entity_id, role, acc_particulars,
            amount, mode, status, created_by, created_at, source_table, journal_id
        ) VALUES (
            v_society_id, 'Cr', CURRENT_DATE, v_acc_ids[i], p_apartment_id, 'apartment',
            COALESCE(p_particulars, 'Maintenance Payment'),
            v_acc_totals[i], p_mode, 'paid', p_confirmed_by, NOW(), 'receivables', v_journal_id
        ) RETURNING id INTO v_trx_id;
        IF v_first_trx_id IS NULL THEN v_first_trx_id := v_trx_id; END IF;
    END LOOP;
END IF;

-- Dr: cash / bank paired side (actual amount received)
IF v_bank_acc IS NOT NULL THEN
    INSERT INTO transactions(
        society_id, entry_side, trx_date, acc_id, entity_id, role, acc_particulars,
        amount, mode, status, created_by, created_at, source_table, source_id, journal_id
    ) VALUES (
        v_society_id, 'Dr', CURRENT_DATE, v_bank_acc, p_apartment_id, 'apartment',
        'Cash received - Maintenance Payment',
        p_amount, p_mode, 'paid', p_confirmed_by, NOW(), 'receivables', v_first_trx_id, v_journal_id
    );
END IF;

-- Excess beyond every currently-open due is banked as an advance-credit
-- row (status='credit') rather than discarded. Use the maintenance account
-- explicitly — overpayment is intended as a maintenance credit, not an
-- unsolicited extra fund contribution.
IF v_remaining > 0 THEN
    INSERT INTO receivables (
        society_id, entity_id, role, acc_id, interest_acc_id,
        description, base_amount, amount, paid_amount, paid_principal,
        status, confirmed_by, confirmed_at, created_at
    ) VALUES (
        v_society_id, p_apartment_id, 'apartment', v_maint_acc_id,
        COALESCE(v_fallback_int_acc, v_maint_acc_id),
        'Advance Credit', v_remaining, v_remaining, 0, 0,
        'credit', p_confirmed_by, NOW(), NOW()
    );
END IF;

RETURN QUERY SELECT v_first_trx_id,
    (p_amount - v_remaining)::NUMERIC(15,2),
    v_remaining::NUMERIC(15,2),
    v_journal_id;
END; $$;
