### **KEY ARCHITECTURAL STRENGTHS**

1. **Rules live in SQL, not UI** — Compliance functions (`fn_*`) are in `estatehub.sql` (lines 13,740–15,800), driven by `regime_rule_parameters` + `rule_parameter_defs`. A society without the regime gets `NULL`/empty, never wrong answers.
2. **Layered Rule Resolver** — `fn_rule()` reads Layer 0 (statute) → 1 (Model Bye-Law adoption) → 2 (Society Policy/GBM) → 3 (Board/MC). Only tighten, never loosen. Statutory rules (`nature='statutory'`) are locked at Layer 0.
3. **Audit Trail** — Every rule change writes to `regime_rule_audit` (append-only via trigger). Financial journals use `previous_hash` chaining (receipts, fund_utilizations, fund_appropriations, fy_closures).
4. **Idempotent FY Close** — `fy_closures` UNIQUE `(society_id, financial_year)` prevents double appropriation; `fn_fy_close_reserve_appropriation` rolls back journal on race loss.
5. **Charge Kind Segregation** — `receivables.charge_kind` distinguishes `common_expense` (subject to bye-law 7, s.22, s.20, s.23) from `transfer_fee` (payable by transferor, not a common expense arrear).
6. **Receipt Payment Log** — `receivable_payment_log` trigger captures every `paid_amount`/`paid_principal` change with `paid_on` date (supports back-dating via `SET LOCAL app.payment_date`), enabling **point-in-time** bye-law 7 / s.22 tests.

### **SUMMARY**

**The codebase genuinely implements UP Apartment Act 2010 / Model Bye-Laws 2011 financial provisions in the database engine**, not just as form labels. The compliance layer is schema-driven, regime-aware, auditable and tested (`test_up_aoa_compliance_live.py`). **Main gaps** are non-financial bye-laws (47-58) and some labour/GST/property-TDS edge cases.

### 2. Bugs found & fixed so far (in `database/estatehub.sql`)
1. **Schema would not install on a fresh database** — `CREATE TABLE borrowing_approvals` referenced `resolutions`
   before that table was created (line ~15224 vs 15525). psql aborted that statement, so `borrowing_approvals` (and its
   index) silently never existed. Fixed by dropping the inline FK and adding `ALTER TABLE borrowing_approvals
   ADD CONSTRAINT borrowing_approvals_resolution_id_fkey FOREIGN KEY (resolution_id) REFERENCES resolutions (id)
   ON DELETE SET NULL;` next to the existing `owner_loans` forward-reference ALTER.
2. **Missing UNIQUE constraint used by two writers** — both `database/seed.py` and `app/services/up_aoa_actions.py::record_borrowing`
   upsert with `ON CONFLICT (society_id, loan_source, principal)`, which raises
   `InvalidColumnReference: there is no unique or exclusion constraint matching the ON CONFLICT specification`.
   Added `CONSTRAINT uq_borrowing_approval UNIQUE (society_id, loan_source, principal)`.
